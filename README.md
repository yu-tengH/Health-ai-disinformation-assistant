# 健康假訊息識讀助理：RAG + LoRA 微調 + ETL 自動化實作專案

結合碩士論文研究發現與本地 LLM 微調技術，打造一個能分析健康假訊息的 AI 助理，並搭配自動化 ETL 管線持續擴充案例資料庫。

## 專案簡介

本專案的知識基礎來自我的碩士論文《影響 AI 生成健康假新聞轉傳之因素》（國立中正大學醫療資訊管理碩士班），該研究以計畫行為理論（TPB）為架構，透過 810 份有效問卷與情境實驗，分析人們分享 AI 生成健康假訊息的心理機制。

我將論文的核心研究發現轉化為訓練資料，透過 LoRA 微調一個本地端小型語言模型，並結合 RAG（檢索增強生成）技術串接真實的事實查核案例，打造出一個能夠：

- 用論文的理論框架分析使用者提出的可疑健康資訊
- 檢索並引用真實查核案例作為佐證
- 對從未見過的全新情境，也能套用學到的判斷邏輯進行分析
- 透過自動化爬蟲持續擴充案例資料庫，不需手動整理

這個專案完整走過「資料準備 → 本地模型微調 → ETL 自動化擷取 → 向量資料庫檢索 → RAG 整合生成 → 網頁介面呈現」的技術鏈路，全程在個人筆電（MacBook Air M5, 16GB）上完成。

## 技術架構

```
                    ┌─────────────────────────────┐
                    │   ETL 自動化管線（可獨立執行）  │
                    │                               │
                    │  scraper.py                   │
                    │  （爬取事實查核中心最新報告）    │
                    │        ↓                      │
                    │  validator.py                 │
                    │  （去重、完整性、長度驗證）      │
                    │        ↓                      │
                    │  併入 fact_check_cases/        │
                    └─────────────┬─────────────────┘
                                  ↓
                    build_vector_db.py
                    （文字轉向量，存入 Chroma）
                                  ↓
使用者問題（Streamlit 網頁介面）
        ↓
RAG 檢索（Chroma 向量資料庫，cosine 相似度比對）
        ↓
組合提示詞（使用者問題 + 檢索到的相關案例）
        ↓
LoRA 微調模型生成回答（mlx-lm + Gemma-2-2B）
        ↓
網頁呈現分析結果（結合真實案例佐證）
```

## 網頁介面

使用 Streamlit 打造互動式網頁介面，讓使用者可直接輸入可疑健康資訊，即時取得結合真實案例的分析結果，無需操作終端機指令。

> 範例：輸入「小黃瓜有特殊功效嗎？」，系統正確檢索到對應案例，並分析出訊息使用「權威頭銜」與「具體數字」營造可信度的手法。

## 技術選型與理由

| 技術決策 | 選擇 | 理由 |
|---|---|---|
| 微調工具 | MLX-LM，而非 PyTorch + PEFT | Apple Silicon 原生框架，在 Mac 上訓練效率較高；概念上與業界常用的 PyTorch + PEFT（Hugging Face）相通，只是語法不同 |
| 向量檢索 | Chroma（HNSW 演算法） | 資料規模小（個位數至數十筆），HNSW 已足夠快速準確；FAISS 專為超大規模（數十萬筆以上）語料設計，此專案規模用不到，屬於過度工程 |
| 檢索距離計算 | Cosine 相似度，而非預設 L2 距離 | 文字嵌入模型的語意相似度以方向（而非長度）衡量更準確，實測後 cosine 距離的排序結果明顯優於預設 L2 |
| 推論展示工具 | Ollama（baseline 測試）+ mlx-lm（正式整合） | Ollama 適合快速互動測試；正式串接 RAG 流程與 Streamlit 網頁時改用 mlx-lm 的 Python API，方便寫進自動化程式碼 |
| 網頁框架 | Streamlit | 開發效率高，適合快速把既有的 Python 邏輯包裝成可互動的展示介面 |
| 爬蟲連結擷取 | 依 URL 規律比對，而非依賴 CSS class | 實際檢視原始碼發現部分 class 名稱含隨機文章 ID（每篇不同），無法重複使用；改用穩定的網址規律（`/fact-check-reports/`）與固定的分類 class（如 `fact-check-report-type-health`）大幅提升穩健性 |
| 生成式檢索（GIR） | 未採用 | 我在論文研究中比較過 PQ VecID、T5 Decoder 等生成式檢索技術，但該類技術的優勢展現在超大規模、高雜訊語料庫，與本專案的乾淨、小規模資料集場景不符，因此選擇更輕量的 Embedding-based RAG |

## ETL 自動化管線

為了讓案例資料庫能持續成長，而非僅依賴一次性手動整理，實作了一套三階段 ETL 流程：

**Extract（`scraper.py`）**：依 URL 規律與固定 class 抓取台灣事實查核中心最新查核報告，解析出標題、查核結果分類、完整內文與主題標籤，存成結構化文字檔。不限定單一主題擷取（實測發現若僅抓健康類，因發布頻率不穩定，經常抓不到任何新資料），改為全量擷取並保留分類標籤，篩選邏輯留到應用層彈性決定。

**Transform（`validator.py`）**：對新擷取的資料做三道驗證——重複資料檢查（比對既有案例編號）、欄位完整性檢查、內容長度合理性檢查，通過驗證的資料才會正式併入 `fact_check_cases/`。

**Load（`build_vector_db.py`）**：將驗證後的完整案例集合，轉換為向量並存入 Chroma 資料庫，供 RAG 檢索使用。

實際執行後，案例資料庫從最初手動整理的 6 則，擴充至 15 則，且新擷取的案例（如「NASA 沙茶醬」案例）已驗證能被 RAG 正確檢索並生成合理分析。

## 實驗過程：從過擬合到找到最佳 Checkpoint

初次訓練（100 iters，未分段監控）大幅過擬合：train loss 降到 0.042，但缺乏中間監控點難以判斷最佳停止時機。加入 `--steps-per-eval 10` 後，觀察到完整的 val loss 曲線：

| Iter | Train Loss | Val Loss |
|---|---|---|
| 1 | - | 5.941 |
| 10 | 4.444 | 3.684 |
| **20** | **2.302** | **3.256（最佳點）** |
| 30 | 1.174 | 3.287 |
| 40 | 0.448 | 3.789 |
| 50 | 0.190 | 3.830 |
| 100 | 0.040 | 4.136 |

Val loss 在 iter 20 觸底後持續回升，確認此為過擬合起始點。最終採用 iter 20 的 checkpoint 作為正式版本（可訓練參數僅佔整體模型的 0.244%，6.39M / 2614.34M）。

### Baseline（微調前）vs 微調後 對比

**問題：什麼是計畫行為理論中的主觀規範？**

- 微調前：完全答錯，將主觀規範誤解為「個人經驗和價值觀」
- 微調後（iter 20）：「對他人觀感的影響力...是一種『我應該怎麼做』的推力」，方向正確且簡潔

**問題：網傳蘋果山楂茶可以瘦身美白降三高，這則訊息可信嗎？**

- 微調前：分析山楂本身的營養成分，完全沒發現這是可疑行銷話術
- 微調後：「並非出自正當健康機構...利用容易被認可的健康標籤製造可信度」，準確點出問題核心

## Demo 展示：RAG + LoRA 整合效果

### 亮點 1：語意理解，而非關鍵字比對

資料庫案例原文為「失智症」，使用者換用同義詞「阿茲海默症」提問，系統仍正確檢索到對應案例：

> **問：** 網路上說吃小黃瓜可以預防阿茲海默症，這樣講對嗎
> **答：** 根據全民查假會社查證，這則訊息為誇大訊息，缺乏充分醫學實證支持。它把單一食材的部分營養成分誇大連結到重大疾病預防...

### 亮點 2：對全新情境的分析遷移能力

以下情境完全未出現在訓練資料或案例資料庫中，系統仍能套用學到的判斷框架進行分析：

> **問：** 網路上有一則貼文說，某醫學中心主任推薦的維他命D保健品，每天吃三顆可以逆轉初期糖尿病，這則訊息你會怎麼分析？
> **答：** 這則貼文內容完全誇大了維他命D的健康效益，並未提供任何醫學研究或證據支持。這則訊息常利用「醫師推薦」的標籤製造高可信度，但這並不代表內容經過專業查核。

### 亮點 3：ETL 新擷取案例可被正確檢索與應用

透過爬蟲新增、從未手動整理過的案例（NASA 沙茶醬謠言），同樣能被系統正確檢索並生成分析，驗證了整條自動化管線的有效性：

> **問：** 網傳影片說台灣沙茶醬被NASA列為標準太空食品，這是真的嗎？
> **答：** 這則訊息最常使用的是「權威頭銜」和「具體數字」。它標示了「NASA」的標籤，讓人覺得訊息來自官方，並附上「標準太空食品」的誇大標示...此外，它還附上了「可減少太空飛船失重」的因果連結，讓訊息看起來更具可信度。

## 已知限制

- **案例混淆**：資料量仍偏小，當檢索同時回傳兩則主題相近但不同的案例時，生成階段偶爾會將兩則案例的細節混在同一段分析中（例如將食物代言案例與熱傷害案例的數字混用）。根本原因是訓練與案例資料規模不足，擴充資料量是最直接的改善方向
- **Embedding 排序偏誤**：目前對整份案例全文（含查核理由、標籤等）做向量化，可能讓次要詞彙稀釋核心語意，導致排序偶有不準確（例如「蘋果山楂茶」案例曾被排到第 3 名而非第 1 名）。已定位原因，計畫改為僅對「謠言原文」欄位做向量化
- **生成重複句子**：小模型 + 小規模訓練資料的組合，偶爾會在生成時重複相同句子，可透過調整重複懲罰（repetition penalty）參數改善
- **來源歸因幻覺**：面對訓練資料庫中未收錄的全新案例，模型分析邏輯正確，但偶爾會誤用「根據 XX 查證」的句型，即使該案例實際上從未被查核過。這是小規模微調常見的幻覺現象，未來可透過提示詞明確要求模型區分「既有案例」與「使用者提出的新案例」來改善
- **資料規模小**：目前案例資料庫僅 15 則，訓練資料 26 組，僅足夠驗證技術可行性，尚不足以支撐大規模實際應用
- **MLX 與 Streamlit 的執行緒相容性**：MLX 的運算資源通道綁定於初始化時所在的執行緒，而 Streamlit 預設會將回呼邏輯派送至不同執行緒執行，導致直接呼叫會出現 `RuntimeError: There is no Stream(cpu, 0) in current thread`。解法是使用單一 worker 的 `ThreadPoolExecutor`（並以 `st.cache_resource` 確保該執行緒池本身不被重複建立），讓模型載入與後續每次生成都固定在同一條執行緒執行

## 未來優化方向

- 擴充案例資料庫至 60-100 則以上，涵蓋更多元的健康假訊息類型，緩解案例混淆問題
- 僅對案例的「謠言原文」欄位做向量化，改善檢索排序準確度
- 將 ETL 管線交由 Airflow 排程，定期自動擷取、驗證、更新向量資料庫，無需手動執行
- 導入 vLLM 部署，測試高併發情境下的服務效能
- 支援多輪對話，讓使用者可針對分析結果進一步追問

## 技術棧

- **微調框架**：MLX-LM（LoRA fine-tuning）
- **基礎模型**：Gemma-2-2B-it（4-bit 量化）
- **向量資料庫**：Chroma
- **嵌入模型**：paraphrase-multilingual-MiniLM-L12-v2
- **網頁介面**：Streamlit
- **爬蟲與資料驗證**：requests、BeautifulSoup4
- **本地推論**：Ollama、mlx-lm
- **開發環境**：MacBook Air（Apple M5, 16GB 統一記憶體）
